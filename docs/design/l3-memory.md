# L0～L3 记忆设计

状态：v0.2.0 已实现核心链路。具体 API、部署预算、保守策略与验证范围见 [实现说明](../layered-memory.md)。本文保留设计目标；文中的拟议字段以运行时代码和实现说明为准。

## 1. 产品边界

Mindsea 是脑海，Memory 是其中的历史知识能力，Future 是对未来和未闭环事项的关注能力。

- **Memory 被动使用**：由模型在需要时调用检索/记住/纠错工具，不在每轮钩子自动注入画像。
- **Memory 内部可主动整理**：采集事件后，在后台提取、归纳、纠错，准备下次被查询的数据。“被动”限定读取和呈现，不要求数据库静止。
- **Future 主动检查**：每轮 DSH 钩子检查候选，有则交给模型择机提起，无则正常聊。
- **Future 更新独立**：任何新证据都能修改事项，不依赖它已被召回，也不等待 L1～L3 整理完成。

第一阶段把分层记忆作为服务端领域能力，DSH 仅负责事件采集、模型调用和工具入口。禁止把分层规则塞进 DSH 钩子或依赖 DSH 会话内的临时变量。

## 2. 层级与职责

这里的 L0～L3 是本项目约定，不是行业统一等级。

| 层                | 保存什么                                                   | 示例                                     | 不负责什么                 |
| ----------------- | ---------------------------------------------------------- | ---------------------------------------- | -------------------------- |
| L0 原始事件       | 原始话语、角色、来源、发生时间、会话和可靠身份             | “以后给我技术结论时，先说重点”           | 不把每句话视作事实         |
| L1 事件与原子事实 | 一次经历、明确陈述、纠正，保留情境和证据                   | 用户在技术讨论中明确偏好先给结论         | 不从单次情绪推断长期性格   |
| L2 主题记忆       | 围绕一个主题的当前事实集合、发展过程、分歧与悬而未决的问题 | 用户对技术沟通方式的历次偏好及例外       | 不把不同场景合并成绝对规则 |
| L3 长期画像       | 有适用范围的稳定偏好、习惯、长期目标、明确关系事实         | 技术说明默认先给结论；评审时仍需完整证据 | 不生成不可验证的心理标签   |

L3 由**可单独更新的画像条目**构成，不是一份越写越长的用户简介。条目可以独立失效、被替代、撤回和解释来源。

L2 是组织层，不是每个事实必须经过的晋升手续。用户明确说出的稳定偏好可以在形成 L1 证据后直接提出 L3 候选；存在的 L2 关联作为补充。不要为了四层齐全而让直接陈述等待无意义的重复确认。

## 3. 关键数据模型（拟议）

### L0：events 与证据片段

继续使用 append-only 事件。新增内容不覆盖原文；纠正是新事件。

- eventId / userId / sessionId / producer / role。
- occurredAt：事件实际发生时间；recordedAt：服务收到的时间。延迟导入不能冒充刚刚发生。
- sourceKind：human、assistant、tool、plugin-context 等来源。身份只能由可信接入端提供。
- 引用证据使用 eventId + startOffset + endOffset + contentHash；偏移统一按 Unicode code point 计数，在服务端校验。
- 转述、引号内内容、假设与助手推断不自动成为用户自己的事实。

### 共同字段：memory_records

| 字段                   | 语义                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------- |
| id / userId / version  | 稳定标识、租户边界、乐观并发版本                                                    |
| layer                  | L1 / L2 / L3                                                                        |
| subjectId              | 用户本人、用户提及的实体，必须在用户命名空间内                                      |
| scope                  | 适用场景；global / topic / relationship / project，不等同于权限                     |
| kind                   | episode / fact / topic-summary / preference / habit / long-term-goal / relationship |
| content                | 人类可读表述，保留条件、例外与不确定性                                              |
| claim                  | 可选结构化谓词和值，例如 response.order = conclusion-first                          |
| basis                  | explicit（明确陈述）或 inferred（有证据归纳），不能由置信分数取代                   |
| status                 | candidate / active / disputed / superseded / expired / retracted                    |
| validFrom / validTo    | 事实适用时间；未知可以为空，不能伪造                                                |
| recordedAt / updatedAt | 系统知晓与修改时间                                                                  |
| reviewAfter            | 需要重新评估的时间，不等同于到期提醒                                                |
| revisionSet            | 创建时依据的用户记忆版本及源版本集合                                                |
| extractorVersion       | 提取策略、提示词与模型版本，用于可重复评估                                          |

数据结构采用各层的判别联合，而不是一个任意 JSON 大对象：L1 强制包含原始证据；L2 强制包含 L1 引用和主题 ID；L3 强制包含 claim、scope、basis 和证据。运行时校验由服务端执行。

### 引用与修订

- `memory_evidence`：记录原始证据片段，以及支持/反驳关系。每条 active L3 都必须能走回有效 L0。
- `memory_dependencies`：有向无环派生依赖，记录精确源版本；同租户校验在服务端完成。
- `memory_revisions`：不可变修订快照、变更原因和触发事件。
- `memory_supersessions`：明确的替代关系；不把所有相反陈述视为覆盖。
- `memory_topics`：稳定主题 ID 与别名，避免同义主题无限增殖。
- `memory_jobs`：独立整理队列与处理进度，不能复用 Future 的完成标记。

同一源事件进入 L1、L2、L3 后仍然只有**一份独立证据**。重放、重复导入、助手复述以及摘要中的复述不能增加支持强度。归纳时按根证据的事件、经历和会话来源去重，而不是按派生记录数量计数。

## 4. L3 的形成规则

### 明确陈述

“以后技术问题先给结论”可以形成限定于 technical-discussion 的偏好。流程为：保存 L0 → 提取 L1 → 校验证据、主体和范围 → 创建 L3 候选 → 按明确陈述规则激活。

“今天别讲太多，我很累”只形成短期情境 L1，不直接成为长期简洁偏好。

### 系统归纳

多次跨独立经历的同类行为可以形成 inferred 候选，但第一版**不自动激活 inferred L3**。需要用户明确确认后才进入 active；确认事件成为新的根证据，并保留此前归纳依据。

这样可以先交付可信的 L3，而不把“模型觉得用户是这样的人”包装成事实。后续若开放自动激活，必须先建立误归纳评估集和可撤回机制，不能只增加一个 confidence > 0.8 条件。

### 纠正和范围变化

“平时简短，但设计评审要详细”新增/修正 design-review 范围的规则，不删除原有一般偏好。

“以后都给完整推导”若确实指向同一范围，替代旧版本。存在歧义时标记 disputed，检索时返回冲突说明或略过，不能悄悄任选一条。

同一作用域的直接纠正优先于更旧的归纳；具体作用域优先于一般作用域；事件发生时间与系统接收时间分别比较，防止延迟导入的旧话覆盖当前状态。

## 5. 写入、整理与失效传播

```text
DSH 原始输入/输出
        │
        ▼
L0 事件持久化 ──────► Future 独立队列 ──────► 事项更新
        │
        └──────────► Memory 独立队列
                         │
                         ├─ L1 提取、去重、反证识别
                         ├─ L2 仅重整受影响主题
                         └─ L3 候选、明确确认与修正
```

L1 可以逐事件或按有明确结束边界的小段对话整理；L2/L3 合并受影响主题后在空闲期批量处理，避免每条消息都全量蒸馏。

重要原则：**纠错失效立即做，重建可以异步做。** 收到明确纠正后，在同一事务中记录反证、将依赖旧事实的派生条目标记不可用，并排入重整队列。重建完成前，被污染的 L3 不继续作为有效事实返回。

处理提交须携带：源事件范围、每个源版本、目标版本、用户记忆 revision。任何相关事实已变化则重读重算；即使“无变化”结果也必须校验输入版本。不能拿旧模型结果覆盖新纠正。

幂等键至少包含 `(userId, jobKind, sourceRange, policyVersion)`。创建记录、写证据关系、写修订、更新搜索 outbox、推进任务进度必须原子提交。

任务状态为 pending → running（有租约）→ done；失败重试，超过预算进入可观察的 failed 状态，并保留重试入口。Memory 整理失败不阻塞 Future，也不永久阻塞后续无关主题；依赖同一主题的任务仍按版本串行提交。

## 6. 读取：保持被动

DSH 不因实现 L3 就增加“每轮加载用户画像”的钩子。默认仍由模型调用 `mindsea_recall`。

拟议的分层查询参数：query、intent、scope、layers、limit、maxChars、asOf。intent 可为 preference / history / topic / exact-quote / auto。

- 偏好类问题优先使用匹配范围的 active L3，同时给出证据入口。
- 某次共同经历优先 L1，主题进展优先 L2。
- “当时具体怎么说”回读 L0，不能把摘要伪装成原话。
- 当前场景的具体例外优先于一般规则。
- 相同事实跨层去重；不会同时灌入 L1、L2、L3 三份重复文本。
- 默认排除 candidate、disputed、失效依赖、superseded、expired、retracted。显式历史查询可查看旧版本，并标明有效期。

结果返回层级、basis、适用范围、有效期、根证据引用、修订版本和截至哪个事件已完成整理。服务返回数据，不替模型决定人格，也不自动发起话题。

Meilisearch 只负责召回。最终必须从 SQLite 重读，并检查用户、状态、范围和依赖版本。索引尚未同步时回退 SQLite；索引中的高相关性不能覆盖已经失效的状态。

第一版维持关键词检索；需要同义召回时再配置混合检索。不得把“存了 L3”写成“已经支持语义理解式搜索”。

## 7. 与 Future 的边界

“周五面试”是 Future；“周五面试结束，用户觉得表现不错”是 L1 经历；“长期在换工作”可归入 L2 职业话题。只有用户明确表达稳定的长期目标，才建立 L3 long-term-goal。

不能将每个 Future 自动晋升为长期画像。Future 的完成状态必须有证据，不由 L2 摘要或时间流逝决定。

Future 可以引用 Memory 证据，Memory 也可引用事项结果事件，但**两个处理队列没有互相等待的循环依赖**。Future 检查的 pending 只关注 Future 队列；Memory 整理落后应通过单独 watermark 表示。

## 8. 撤回、遗忘与重新整理

用户撤回一条事实时，将其及依赖派生内容标记 retracted，并更新索引。用户要求删除原文时，按明确范围处理根证据和派生条目，保留必要的无正文 tombstone 防止重放复活；不要把“忘记”实现为仅删除索引。

从旧会话回放时必须检查 tombstone。引用已删除证据的 L2/L3 不能自动恢复；如果还有其他独立证据，重新审查后再生成新版本。

修改整理模型或提示词时，可重建派生层，但不更改 L0，不覆盖手工纠正/撤回决策。重新生成也要经过版本检查和相同激活规则。

## 9. 从现有结构迁移

- schema v2 的 `events` 继续作为 L0 基础；补 producer、recordedAt 和证据片段能力时使用显式 v3 迁移。
- 现有 `kind=memory` 不一刀切改成 L3。没有可追溯证据的条目标为 legacy/unverified，保留读取入口但不作为已验证 L3。
- `future` / `loop` 保留独立事项模型和现有行为，不能在迁移中混入 memory_records。
- 新分层表先增量写入，保留旧 API；明确标记来源与层级后逐步切换 `mindsea_recall`。
- 迁移版本在事务完成后才推进；迁移失败必须回滚；建立升级和重复启动测试。

## 10. 分期实施与验收

### A：证据与 L1

实现证据引用、L1 记录、版本与反证，补 Memory 独立队列。验收：原话可回读、引用偏移可验证、不同用户不能互引、重放不重复、助手猜测不形成用户事实。

### B：L2 主题组织

增量更新受影响主题，保留发展过程和例外。验收：跨会话同主题能汇合，独立主题不互相污染，同一根证据不会因重复摘要被放大。

### C：L3 明确偏好与长期事实

实现原子画像、scope、明确陈述激活、inferred 候选待确认、失效传播。验收：单次疲惫不成为长期性格；具体例外不覆盖所有场景；新纠正提交后旧画像立即退出正常检索。

### D：检索与 DSH 验收

增加分层检索、来源解释与历史查询，保持被动工具入口。验收：每轮 Future 钩子不调用 Memory；无相关事实时不补造画像；Memory worker 失败不阻塞 Future；遗忘后重放不复活。

每期需有真实 SQLite/HTTP 回归与确定性模型替身测试。语义质量另用人工标注的多轮对话集评估，至少记录错误归因、错误晋升、旧结论残留、范围误用、证据重复计数和召回遗漏，不能只用 schema 校验通过率作为 L3 效果。

## 11. 计划中的文件落点

- `src/contracts/memory.ts`：分层 DTO 与校验，只有开始 A 阶段时创建。
- `src/application/memory/`：提取、归纳、激活、失效传播及任务编排。
- `src/storage/sqlite/memory-*.ts`：分层记录、证据、任务仓储和显式迁移。
- `src/http/routes/memory.ts`：分层记忆 API，保持薄适配。
- `plugins/dsh-mindsea/src/`：宿主模型适配和被动工具；不放 SQL 或晋升规则。

核心模块已按职责落地。与原设计的差异：L1/L2/L3 采用单次有界增量批次，尚未采用分层独立定时蒸馏；重建策略使用当前 policyVersion；撤回采取保守的事件级来源屏蔽。
